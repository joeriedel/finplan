# finplan design

This document describes finplan's data model, projection engine, analysis tools and agent access. It records decisions, not code: where the code and this document disagree, one of them is wrong and should be fixed. It describes capabilities only; a user's own accounts, household and numbers are data entered into the app, never written here or anywhere in the repository.

Status: agreed design. The data model, asset rules and a placeholder projection engine with breakdowns exist as standalone libraries (`internal/model`, `internal/engine`) that import only the standard library; the Graph and Projections tabs use them. Financial rules are placeholders (see Implementation notes); market classes, shocks and rebalances have types only.

## Principles

- **The record is append-only.** What actually happened is never rewritten. Any entry can be corrected at any time; the UI feels like an edit, but stores a correction that supersedes the original, which is kept and viewable.
- **Store inputs, never computed output.** Projections store only their inputs, so engine fixes and improvements refine every projection, old ones included.
- **Stored formats load forever.** Old inputs are migrated, never dropped.
- **One code path.** The GUI and the CLI change data only through the same library functions, so neither can bypass a rule the other enforces.
- **Every number is explainable.** The change in any account over any interval breaks down into its causes (income, expenses, tax, growth, transfers, shocks), for the UI and for the agent.
- **The engine is a standalone library** with its own tests, separate from the UI.

## Accounts

An account is naked data: a balance history, a transaction history (and, for investment accounts, holdings), plus descriptive attributes. Attributes are facts, not behavior. Examples:

- type: checking, savings, credit card, brokerage, 401k, TSP, IRA, Roth IRA, HSA, 529, mortgage, loan, equity (RSUs), property (such as a home)
- tax treatment: taxable, tax-deferred, tax-free, 529
- a stated interest rate, which serves only as a default when the account is projected

Liabilities carry negative balances.

An account can be closed on a date (`Account.Closed`). It keeps its history and its balance on the close date, and reads 0 on every later date (`ClosedOn(d)` is true only after the close date; the engine returns no data for such a date). A budget item that touches a closed account, as its account, from or to, stops after the close date on both sides, in every projection, so a transfer neither drains an account into a closed one nor creates money out of it. Closing is refused for an account a projection defines, one already closed, a date before the account's last record entry of either kind (`Account.LastEntry`) and a date before a non-voided entry of another account that names it as its counter account; reopening clears the date. A new snapshot, transaction or correction dated after the close date, or a transfer whose counter account is closed on its date, is refused. An account with no record entries, that no other account's entry names as counter and that nothing refers to can be deleted instead; otherwise it is closed. Closed accounts are left out of the pickers for new Graph lines, modification targets and budget item accounts; existing lines, modifications and items keep working.

Accounts come from aggregation (SimpleFIN Bridge, including holdings where the institution provides them), from file import, or from manual entry. A projection can also introduce hypothetical accounts.

### Transactions

Each transaction is classified as **income**, **expense** or **transfer**. A transfer moves money between two of the user's own accounts and is never spending: a credit card payment from checking is a transfer, otherwise every card purchase would count twice. Classification and categories are corrections layered over the synced rows, so the synced data stays untouched.

## Assets

An asset carries behavior. It wraps one or more members, each of which is an account or another asset.

- Every account has a **default asset** wrapping it alone, which surfaces the account's attributes (such as its interest rate) as defaults.
- An **aggregate asset** wraps several members, for example "all cash" over every cash account, or "net worth" over everything (liabilities are negative, so net worth is a plain sum). A rule-based aggregate also picks up the hypothetical accounts of the projection it is evaluated under (see Projections); the demo's Net worth is a single all-accounts rule member.
- Membership is an explicit list, a rule (for example: type is cash, so newly linked accounts join on their own), or both.
- Names are unique: creating or renaming an asset or an account is refused (`ErrNameTaken`, CLI code `name_taken`) when the trimmed name matches, ignoring case, another asset or any other account; changing only the case of one's own name is allowed. The check is wider than that for assets: an asset's name may also not equal the name of any projection's account (`freeAssetName`), and a new or renamed projection account may not take an asset's name (`freeProjAccountName`; the default assets of record accounts are not counted). Record and projection accounts may share names. The refusal's reason names the clash. Data that already clashes still loads, and an edit that keeps the name is allowed. Ids made from a name can still collide with other ids and are then refused too.
- Assets nest freely; they form a graph, and cycles are rejected.

Money lives only in accounts. Any asset can be asked for its balance on any date.

### Default balances

Every account and asset has a **default balance**: a fallback value for dates with no actual data. It is not added to anything and it does not grow; growth is a projection concept.

- A **base** default of 0 fills every date.
- The user can add **intervals** (from, optional to, value) that override the base on those dates (a missing `to` leaves the interval open-ended, and `to` is inclusive), for example "use 40,000 for this account until its real data begins".
- **Actual data always beats any default.** Defaults apply only on dates with no actual data.

**Projection defaults.** Under a projection, `default` modifications (set or scale, over a date range) change an account's or asset's default (`model.ModifiedDefault`). They are layered over the base default in chain then list order, the last applied winning. A set modification gives its value on the dates its segments cover; a scale modification multiplies the default beneath it and has no effect where there is none; outside its segments the base default is unchanged. The record is never changed. Actual data still wins: a projection default is used only where the base would use a default, on dates with no actual data up to the projection start; after the start, balances are projected from the value at the start. An `account:` target, or the account's default asset `acct:<id>`, changes the account's default; any other `asset:` target changes that asset's own default, which applies only when no member account has data. On a projection-defined account a default modification gives no balance before the opening date, and its value on that date becomes the opening change in the Breakdown. The overwrite check matches default modifications by exact target, not by the accounts under it.

A balance query returns the value with a flag saying whether it came from actual data or from defaults.

An account has actual data on every date within its real data span; gaps between snapshots inside the span are filled from transactions, never from defaults. An asset's **actual-data coverage** is the union of its members' coverage, which may be disjoint, and its **last actual data date** is the end of that union.

### Resolving an asset's balance

Actual data comes only from accounts; defaults never count as actual data, however deeply nested. For an asset on a given date:

- If any underlying account has actual data on that date, the asset's value is the sum of its members, each resolved the same way (its actual data, its own default, or 0).
- Otherwise, if the asset has a default interval covering that date, that value wins over its members' defaults.
- Otherwise, the asset's value is the sum of its members, each resolved the same way. The 0 base never beats a member's explicit interval.

Hand-offs between defaults and actual data can make a line jump; that is accepted and marked on the graph.

Any asset can be graphed and projected, individually or as an aggregate, by the user or by the agent.

### Overlap

An asset must never count an account twice, but nothing is refused. When a member would count something already included (for example, checking is already in the asset through "all cash"), that member is accepted but marked invalid: shown red with an error icon and a tooltip naming the duplicate, and left out of the sum. The user fixes it however they like. When members overlap, the later-added member is the one marked invalid, so the result is deterministic.

The check runs whenever an asset is used, not only when it is edited, because editing a wrapped asset can create overlap later. The same red marking gives immediate feedback while building an asset.

## Parameters and precedence

Every behavioral property is a parameter: growth rate, allocation, contribution rules, withdrawal order, and so on. Every parameter is a **schedule over time**: piecewise values by date range ("4% until 2029, then 6% until 2035, then 2%"). A constant is a schedule with one segment.

A segment has a start (`From`), an optional end (`End`) and a value. The end is inclusive, so a segment covers [From, End], like `BudgetItem.End` and `Interval.To`. A segment that touches the next has no end: it runs until the day before the next segment's start, or indefinitely if it is the last. Segments are sorted by start and never overlap: an end must be before the next segment's start, and an end may equal its own start (a one-day segment) but not precede it. `NewSchedule` rejects an unsorted, duplicate or overlapping schedule, and an end before its start, with an error, and since segments are unexported every schedule goes through it. It normalizes touching to one representation: an end on the day before the next start is dropped, and an end of `MaxDate` is dropped as no end. An earlier end leaves a gap.

Dates that no segment covers (before the first segment, in a gap, or from the last segment's end on) are not covered by the setting, and the value beneath shows through. A setting's start is its first segment's start and its end is its last segment's end; there is no separate setting-level start or end. Compound growth over dates no segment covers contributes no growth.

Settings apply **in order, the last applied winning**. For each account on a line (a line is an asset queried under a projection), the value starts as the account's own (for growth, its stated rate). Settings are then applied in sequence, each overwriting the value for the accounts it covers, on the dates its schedule covers; what remains is the value. There are no modes and no specificity rules: the order alone decides.

The order is:

1. **Asset definitions.** An asset can set the parameters of anything it wraps. Along the path from the account to the line's asset, the account's own (default) asset comes first, then inner assets before outer ones, and unrelated assets in scope order; within one asset, list order. A variant such as "all cash at 5%" is a new asset wrapping "all cash" and setting 5%, which leaves "all cash" untouched everywhere else.
2. **The projection's parent chain**, oldest ancestor first, each projection's settings in list order.
3. **The projection's own settings**, in list order.

"All cash 7%" followed by "Checking 1%" gives Checking 1% and every other cash account 7%; in the reverse order Checking gets 7%. Overlapping siblings need no conflict rule: the later one wins.

Settings layer per covered date: a later setting overwrites the value beneath only on the dates its segments cover, and the earlier value stands everywhere else. A constant covers every date, so it overwrites entirely. This applies to growth and other parameter settings on asset definitions and in projections, to global inflation modifications and to budget item amount changes; inflation and amount modifications no longer replace the whole value.

A modification has a **mode**: `set` (the default; an empty mode and `set` are the same, and a stored projection without a mode loads as `set`) or `scale`. A set modification overwrites the value beneath as described above. A scale modification multiplies the value beneath it at each date (the base plus earlier modifications, in chain then list order; `Schedule.Scale`, `Modification.Over`), so it follows later changes to the base: "cut dining 30% from 2026" is a scale of 0.7 on the dining item's amount. Where nothing is beneath, the date stays unset. Scale is allowed on amount, growth (account, asset and budget item) and inflation, not on `add_item`, and its multiplier must be finite and at least 0. A later scale never overwrites an earlier modification in the overwrite check, while a later covering set overwrites an earlier set or scale.

Per-asset start and `override_history` follow the same order but are single values with no segments: each setting replaces the one before it (the last wins). They are projection settings, never properties of an asset definition: "Retirement 2024" followed by "TSP 2020" gives the TSP its 2020 start.

A projection's setting reaches every account under its target asset on every line queried under that projection, even when the line's asset does not contain the target; a setting aimed at an account reaches just that account. An asset-definition setting applies only on lines whose asset is, or contains, that asset. An account may therefore show different values on different lines; that is intended. A setting that names an unknown asset is an error.

The UI keeps a projection's modifications ordered and reorderable (drag a row). A modification is greyed, with a tooltip naming the later modification that overwrites it, when a later one in the chain (ancestors root first, then the projection's own, each in list order) has a schedule that covers every date of its schedule and, for an account or asset target, covers an account it covers (`Record.OverwrittenMods`, using `Resolve` for the accounts and `Schedule.Covers`); when that holds for only some of the accounts the tooltip says so (`Overwrite.Partial`). Budget item and global modifications are overwritten by a later one with the same target and property. Budget item additions are never marked. Marking an overwrite per account in the setting editor is not built.

The engine still computes each account individually, because flows land on accounts and tax treatment differs per account; the assets supply the resolved parameters.

## Budgets

The budget is the forecast of every flow, and the shared context for extrapolation: every asset is extrapolated against the same budget, so "all cash" and "net worth" always agree about the same accounts.

A budget item has:

- an amount, which is a schedule (`model.Schedule`): a single number is one segment, and segments let it change on dates (for example a daycare cost of 1400 until a date and 600 after); every segment must be above zero
- a recurrence (`Recurrence`): one-time, weekly, biweekly (every 2 weeks), semimonthly (two chosen days of the month), monthly (a day), quarterly, annual (month and day) or custom (every Count days, weeks, months or years, Count at least 1)
- a start date, required for a new item, and an optional end date (the end is inclusive; a missing end means open-ended; an older item may have no start)
- whether it is indexed to inflation
- an optional annual growth rate (a raise, as a fraction: 0.03 is 3%), also a schedule; an empty one means no raises
- the account it lands in or draws from

The dates of an item are `BudgetItem.Dates`. The interval kinds (weekly, biweekly, quarterly, custom) are phased from the recurrence's anchor when it has one, else from the item's start; one-time uses its anchor (a new one-time or biweekly item may give its date as the anchor in place of a start). Month-based steps (quarterly, custom months and years) keep the phase's day of the month and a day past the end of a shorter month falls on that month's last day without drifting afterwards; so do monthly, semimonthly and annual days 29 to 31. There is no "bimonthly" kind.

A raise steps the amount up once a year, on the anniversary of the item's start (else its recurrence anchor, else the record's `Today`), not continuously. It combines with inflation indexing. The growth schedule can be set on the item and changed by a projection modification of the item's `growth` property (set or scale); the rate in effect on each anniversary is used. The amount in effect on each date comes from the amount schedule (as changed by amount modifications); a date it does not cover pays nothing.

Items cover income (gross salary, RSU vests, bonuses, pensions, Social Security) as well as expenses. Matching rules (payee, category, account) map transactions to budget items, so baselines can be derived from history and actual spending compared with the budget.

Taxes are not budget items. The engine computes them (see Taxes), and the net pay after tax and payroll deductions is what lands in the account.

### Past and future

The engine reads back actual data where it applies and uses budget items after that. Where that switch happens is set by the projection start rule (see Projections).

## Projections

A projection is a named set of hypothetical modifications layered over the base (the real accounts and assets plus the base budget). It stores only its changes, never a copy, so corrections to the base flow into every projection.

A projection can modify **any property of any object on a timetable**: a modification is an object, a property and a schedule of values. This covers, for example:

- budget changes: add, change or end an item on a date ("new job in March 2027", "cut dining 30% from 2026"); dated budget changes are what other tools call events
- parameter schedules ("brokerage at 4% until 2029, then 6% until 2035, then 2%")
- one-off actions: a market shock ("large cap −30% in March 2035"), a rebalance ("brokerage to 75% treasuries, 25% small cap in 2027"), a withdrawal or transfer
- hypothetical accounts (see Projection accounts) and default balances (a `default` modification over a date range, see Default balances)
- the projection start date, globally or per asset, and `override_history` (see below)
- global assumptions such as inflation

A projection may build on one parent projection (a chain, never a merge of two). A modification whose target no longer exists, for example a change to a budget item later deleted from the base, is marked red and skipped, as with overlap (`Record.MissingTargets` says which modifications; the Projections tab draws them red and `projection show` marks them `missing`). The shared edit operations (`internal/ops`, used by the GUI and the CLI) keep this from arising through an edit: they refuse a move, removal, parent change or removal of an added item that would leave a modification that resolved before unresolved, and a new modification whose target does not resolve at its position; modifications already dangling do not block an edit.

### Projection accounts

A projection can define **accounts of its own** (`model.ProjAccount`): id, name, type, tax treatment, stated rate, opening balance and opening date. They exist only under that projection and the projections built on it and are never written to the record's accounts. `Record.For(projection)` returns the effective record: the base plus the accounts of the projection's chain, root first, each with its default asset (so rule-based aggregates such as All cash and Net worth pick them up); a child inherits its ancestors' accounts.

- An id may not collide with a base account or asset id or with one in the projection's chain or descendants; siblings may reuse ids. Creating a record account or asset with a projection account's id is refused, and so are a parent change and a GUI undo or redo that would cause a collision.
- Before its opening date a projection account reads 0 (no data). On the opening date it holds the opening balance plus that day's flows, and from then it grows at its stated rate (and any growth modifications), even when the opening date is before the projection start.
- A budget item touching a projection account counts on all sides only after one shared cutoff, the latest of each touched account's own cutoff: for a record account its usual start; for a projection account the day before it opens when that is after the projection start, otherwise the projection start. Occurrences before an account opens are not modelled on any side.
- A breakdown whose window contains the opening date has an `opening` line for the opening balance.
- Removing an account is refused while a modification, item or asset setting in the projection or a descendant references it.
- Amortization stays deferred. A mortgage is a debt account with a negative opening balance and its interest as the growth rate, paid down by a monthly transfer item. To model a house purchase: the home is a property account (purchase price as opening, appreciation as rate), the mortgage a mortgage account, the down payment a one-time transfer from Checking to outside, and the payment a monthly transfer from Checking to the mortgage.

### Querying the engine

A projection does no computing of its own. It asks the engine what its assets will hold, passing in every modification in effect:

    engine.balances(target, sample_times, modifications)

Reality is the same query with no modifications. The engine is a pure function of the record, the base budget, the modifications and the engine version, so the same inputs always give the same answer and results can be cached; the GUI and the CLI see identical numbers. A query takes a set of sample times (or a range and a resolution), so one simulation serves a whole graph. Extrapolation continues indefinitely; the caller decides how far to look.

A plotted line is an asset under a projection, or under reality. A report is an asset viewed over a time range.

### Projection start

A projection has a global **projection start date**. Each asset in it may be given its own start date, and its own `override_history` setting. The engine applies the rule to each account, using the start date and `override_history` resolved from the projection-wide values, over which the per-asset settings covering the account are applied in order (see Parameters and precedence):

    if override_history:
        start = min(last_actual_data_date, projection_start_date)
    else:
        start = last_actual_data_date

- Without `override_history`, all real data is read back, and each account starts projecting where its own data runs out. Checking synced through yesterday projects from tomorrow, while a hand-entered account last updated in March projects from March, under the same projection.
- With `override_history`, real data after the projection start is ignored: the "what if I had done this back then" case.
- An account with no actual data starts at the projection start date, reading back its defaults before it.

Before its start, an account's values are read back; from its start on, the engine extrapolates from the value at that point, applying the projection's modifications. Real data therefore beats modifications on the dates it covers, unless the start moves earlier.

The engine **aggregates as it projects**: every account is read back or projected on its own, and an asset's value is the sum of its accounts. A member whose data ends earlier than its siblings' is projected from its own end, never filled with defaults.

### Scope

Extrapolating an asset computes only the accounts under it. A transfer to an account outside it counts as money leaving. Income comes from the budget regardless of scope, and taxes are computed for the household as a whole, so a narrow asset ("all cash") still sees correct net pay.

## Market classes and holdings

Returns come from **market classes** (treasuries, large cap, small cap, international, cash, and so on), not from accounts. An account's growth is its allocation across classes times the classes' returns. A plain fixed rate, such as a savings account's interest, is a single fixed-rate class, so simple accounts stay simple.

- Each investment account tracks a **sub-balance per class**, filled from holdings: each held symbol maps to one or more classes (a target-date fund is a blend whose mix changes over time; TSP funds map one-to-one).
- Allocations drift between rebalances; a **rebalance** is an explicit dated action.
- A **shock** hits a class, and each account takes it in proportion to its exposure.

### Real market data

Classes are pinned to real data for the past and for defaults; the future stays an assumption the user can override.

- Class history comes from real total-return series (adjusted close, dividends reinvested) of a proxy fund per class. It drives projections starting in the past, splits real balances between syncs, and supplies return sequences for Monte Carlo.
- Each class's default forward return is its long-run historical return.
- TSP fund share prices come from tsp.gov.
- The price source is not yet chosen; providers' adjusted closes differ slightly, so the first market-data work should compare them.

## Cost basis

Taxable accounts track cost basis as dated purchase lots per market class, sold oldest first or by the broker's method. RSUs track exact lots per grant and vest, because each vest's price sets its basis.

Trades inside tax-advantaged accounts (401k, TSP, IRA, Roth IRA, HSA, 529) are never taxed. In a taxable account, a rebalance or withdrawal realizes gains (short-term or long-term by holding period) that feed that year's taxes. Rebalancing with new money involves no sale.

## Taxes

The engine computes taxes from income, realized gains, contributions and deductions, using tax rules shipped as engine data, versioned in code: brackets, standard deductions, credits and contribution limits by year, with rules for extending them past the last known year (indexed to inflation). Tax rules are engine data, not projection inputs.

Scope: US federal and Virginia, modeled properly; no generic multi-state support. Filing status, dependents (including the child tax credit), the Virginia 529 deduction, early-withdrawal penalties and the net investment income tax are in scope.

Withholding, estimated payments, refunds and amounts owed are what land in accounts. At each year end the engine reconciles tax due against tax paid.

## The engine

The engine is event-driven, with no fixed time step. It advances from one dated flow to the next (each paycheck, bill, vest, contribution, shock and rebalance on its actual date) and grows balances over exactly the time elapsed between them. Granularity is therefore not a property of the engine: `balance(t)` is defined for any instant, and the caller chooses how to sample it (the graph by its zoom level, a report by its interval, the CLI by a flag). Zoomed out over decades the graph samples sparsely; zoomed in on a month it shows each paycheck landing.

- **Growth** compounds by each account's own convention: daily for credit-card interest, per period for a mortgage's amortization schedule, and continuously over elapsed time for market classes.
- **Ordering on one date:** income, then payroll deductions (401k/TSP and employer match, HSA, withholding), RSU vests taxed as income, expenses, debt payments, then contributions and where leftover cash goes (a waterfall), then shocks and rebalances. As built so far, one date's changes apply in the order opening, income, grant (a new RSU grant), vest, expense, transfer (`rankOpening` to `rankTransfer` in `internal/engine/engine.go`).
- **Taxes** are computed per tax year, because that is how they work: withholding and estimated payments flow on their dates, and each year end reconciles tax due against tax paid.
- **Breakdowns** cover any interval the caller picks.
- **Monte Carlo** draws class returns at a chosen base resolution, since randomized returns need a step; the rest of the engine is unchanged.

Capabilities the engine must model: 401k and TSP limits, employer match, RSU vesting and sale, mortgage amortization, 529 rules, inflation, FERS pensions (annuity, the supplement before 62, survivor options), and retirement drawdown (withdrawal order, Social Security, required minimum distributions, Roth conversions).

The engine must be fast: goal solving and Monte Carlo rerun it thousands of times. Sixty years of biweekly pay and monthly bills is a few thousand events per run.

## Implementation notes

Details the build settled, and the placeholders it uses until the real rules arrive.

**Layout.** Model types and asset rules are in `internal/model`; the engine is in `internal/engine` and imports the model. The invented family-of-six dataset (`demodata.Family()`, reference date 2026-11-08; 13 accounts, among them the equity account `equity`, see "Equity: RSU grants") is in `internal/demodata`; the older `demodata.Generate` is gone.

**Dates and growth.** Dates have day resolution. Growth compounds annually over exactly days/365.25.

**Query.** `engine.Balances(record, projection name, target asset, sample times)` takes its modifications from the named projection and its parent chain; an empty name means reality. `Record.Today` stands in for the clock and is the default projection start.

**Sample status.** Each sample is actual, projected, partly projected (an aggregate with some members projected) or default (no underlying account has data).

**Projection start.** The projection-wide start (default `Record.Today`) and `override_history` (default false) are taken from the last projection in the chain that sets them; they are the base value, and the per-asset settings that cover the account are applied over it in order.

**Precedence.** Settings are applied in order, the last winning (`model.Apply`): asset-definition parameters first (`Resolution.AssetsAround`: the account's default asset, then inner before outer assets; `Resolution.GrowthLayers` returns these growth layers, after the stated rate, with the effective schedule, and is used by both the engine and the Assets tab), then the projection chain root first, each projection's settings in list order. A schedule is written over the prior one on the dates its segments cover (`Schedule.Overlay`), so gaps and ends let the value beneath show through; start and `override_history` simply replace. A projection setting covers an account when it lies under the setting's target (resolved separately, so the target need not lie within the line's asset); an asset's own parameters cover only accounts it wraps within the line's scope. An `AssetSetting` naming an unknown asset is an error.

**Overlap.** The later-added member (by a record-wide sequence) is invalid as a whole, rule members included, is named with its duplicate and is left out of sums. It is checked on every resolve. A rule matching no accounts contributes 0; an empty rule matches every account. Default asset ids are `acct:<id>`.

**Actual data span.** From the earliest to the latest snapshot or transaction; an account needs at least one snapshot. An equity account with grants is the exception: its span runs from its first grant to its latest grant, vest, price observation of a stock it holds, or transaction (see "Equity: RSU grants"). Between snapshots the balance is the earlier snapshot plus transactions; before the first snapshot it is counted back from it.

**Breakdown.** `engine.Breakdown(record, projection, target, from, to)` covers (from, to]. Lines are split by cause and by actual (read back) versus projected. Causes: income, expense, transfer, contribution, withdrawal, tax, growth, opening (a projection account's opening balance), grant (the value of a new RSU grant added to an equity account), vest (the net proceeds of a vest, which leave the equity account for the deposit account), unexplained (snapshot jumps not covered by transactions, and for an equity account whatever its grants, recorded vests and price moves do not explain) and default. For an account that holds grants, the read-back of a past window attributes recorded grants to `grant`, recorded vests to `vest` (minus the net proceeds) and `tax` (minus the withholding W) and price changes of the shares held to `growth`, leaving the rest as `unexplained`; a vest recorded at a price that differs from the price book's on its date leaves that difference in `unexplained`. A brokerage transaction tied to a recorded vest (`RecordedVest.TxEntry`, resolved when the record loads to `model.Transaction.Entry` by `linkTies` in `internal/store/record.go`) reads back as a transfer from the equity account. Projected vests and grants are attributed in the same causes (see Equity: RSU grants). A `default` cause absorbs changes from default balances so the lines always total the balance change; residues under 1e-6 are dropped. Transfers with both sides inside the target cancel.

**Transfer classification.** Unsheltered to sheltered (tax-deferred, tax-free, 529) is a contribution, sheltered to unsheltered a withdrawal, anything else a transfer. A transfer to an account outside the target's scope counts as money leaving.

**Placeholder rules.** Tax is 25% of gross on income flows; a withdrawal from a tax-deferred account also charges 32% tax on top, to the source, with no penalty. On one date the engine applies opening, income, grant, vest, expense, then transfers (the full order under The engine is not yet modelled). Indexed budget items scale by the global inflation schedule compounded from `Record.Today` to the flow date; history is never indexed. An item's amount is its resolved amount (after amount modifications) times its raise factor times, if indexed, the inflation compound (`raiseFactor`, `path.build`). The raise factor multiplies `1+g` for each anniversary after the later of the anchor and `Record.Today`, up to the flow date, using the growth in effect on that anniversary; a step factor is clamped at 0, and a Feb 29 anchor falls on Feb 28 in other years.

**Modifications supported.** A budget item's `amount` and `growth` schedules (each set or scale), an account or asset `growth` schedule, an account or asset `default` schedule (see Default balances), global `inflation` (set or scale), a stock's `growth` (target kind `stock`, the id being the symbol; set or scale), `add_item` (adds a whole budget item) and `add_grant` (adds a focal grant to an equity account, see Equity: RSU grants). Unsupported properties and dangling targets are skipped and reported in the result's diagnostics.

### Equity: RSU grants

The model, storage, shared operations and CLI, the Equity UI and the engine's projection of vests, stock prices and focal grants (with attribution in the breakdown) are built. W as tax paid toward the year is not modelled, and feed and transaction matching remain unbuilt.

**Vest calendars** (`model.VestCalendar`) are named documents (kind `calendar`) shared by the grants of one employer. A calendar has one rule per month, either a fixed day of the month or the 1st to 4th or last weekday, and overrides that each move one generated date to another. `Validate` refuses a month outside 1 to 12, two rules for a month, a rule that does not set exactly one of day and Nth weekday, a fixed day that does not exist in every year (so February at most 28, and 31 in a 30-day month), an override whose From is not a generated date, an override that does not move its date, and a date overridden twice. `Dates(from, to)` lists the generated dates with overrides applied.

**Grants** (`model.Grant`, held on the equity account) have a symbol, a date, a share count (entered as shares, or as a dollar value that buys the whole shares at the grant price, rounded down), a reference grant price (each vest is valued at the price on its vest date, not this), a calendar, a first vest date (a date of the calendar), year percents, an optional cliff, a vest percent for each planned vest, withholding rates and a brokerage account. Each year's percent is split equally over that year's calendar vests (`GeneratePercents`); the percents of the vests before the cliff, measured in calendar months from the first vest's month, are merged into the first vest on or after it, as one planned vest on that date (`PlanDates`). The per-vest percents can be edited and must sum to 100. `Grant.Plan` turns them into planned vests: shares are rounded down with the remainder on the last vest. Withholding rates default to 22% federal, 5.75% Virginia and 7.65% FICA (`DefaultWithholding`).

**Recorded vests** (`model.RecordedVest`) say that a planned vest happened, on its date and with its shares or on others: value V is shares times the price, W the withholding (V times the rates, or an amount entered), and net N = V - W. `ops.RecordVest` saves, together, the vest, a price observation of the stock on that date (unless one with the same price is there) and a transfer of N into the grant's brokerage account with the equity account as counter; with an existing brokerage entry id (tied) it records the vest against that deposit and no second one (`checkTied`). A planned vest is recorded once. A vest is refused before its grant's date or when it has more shares than the grant has left (`checkVest`). Correcting or voiding a vest does not touch its deposit or its price observation; those are corrected or voided on their own.

**Stock prices** (`model.PriceObservation`, in `Record.Prices`) are a symbol, a date and a price.

**Equity balance.** An equity account with grants has no snapshots: its balance on a date is, for each grant dated on or before it, the unvested shares (granted less those vested by then) times the stock's latest price observation on or before it, or the grant price before any observation (`Account.equityAt`). It replaces snapshots for the account: `AddSnapshot` refuses an equity account, but an equity account with no grants still reads any legacy snapshots. Readers get the value through the same `Account.ActualAt`, `Span` and `LastEntry` path as for any account.

**Stock growth.** A stock, keyed by its symbol, has a growth schedule (`Record.StockGrowth`, `model.Record.StockGrowthOf`), default 0%, stored as an editable document of kind `stock`. `ops.SetStockGrowth` (`internal/ops/stocks.go`) and the CLI `stock growth <symbol>` set or clear it; the GUI has no editor for the base schedule. Projections change it with a modification of target kind `stock` (`mod add --target stock:<symbol> --property growth`, or the Projections tab's Add form), set or scale, which the timeline strip editor also edits (`ops` validates it in `checkTarget`).

**Projected price** (`newStockPrices`, `stockPrices.at` in `internal/engine/equity.go`). Each equity account path has its own prices: each symbol is anchored at the price book's price on the path's start (`PriceBook.At(symbol, start)`) and compounds from the start by the stock's growth with the projection's modifications applied; price observations after the start are ignored. With no observation on or before the start, each grant is anchored at its own grant price (a grant dated after the start compounds from its own date), and the focal grants of such a symbol use the price path of the latest earlier grant, or are skipped when there is none.

**Equity projection** (`internal/engine/equity.go`, `engine.go`). A projected equity account's balance is its unvested shares times the projected price; the account's stated rate and growth modifications of the account or its default asset do not apply (they are reported in the diagnostics as skipped, "an equity account is worth its shares at the stock's price: change the stock's growth instead"). Each planned vest that no recorded vest on or before the start fulfils happens on its date after the start, and an overdue one (on or before the start) on the day after the start: the equity account loses the net proceeds N (cause `vest`, the counter being the deposit account) and the withholding W (cause `tax`), and the deposit account gains N as a `transfer` from the equity account. Projected vests are capped at the shares the grant has left, and with override history a vest recorded after the start is projected too. Real grants dated after the start add their value on their date (cause `grant`).

**Focal grants** (`model.FocalGrant`, `internal/model/focalgrant.go`) are a modification with property `add_grant` targeting an equity account: a grant that does not exist in the record, either one-time or yearly on the month and day of its date up to an optional last date, valued in dollars and converted to shares (rounded down) at the projected price on the grant date. It has a vest calendar, year percents, an optional cliff, the months after the grant before the first vest (the first calendar date at least that many months after it), withholding rates (default 22%, 5.75% and 7.65%) and a deposit account, which must be a brokerage account (`checkFocalGrant` in `internal/ops/mods.go`). Only grant dates after the equity path's start are generated, up to the queried horizon. The CLI sets one with `mod add --property add_grant` and its flags (`--symbol`, `--value`, `--from`, `--end`, `--yearly`, `--calendar`, `--year-percents`, `--cliff-months`, `--first-vest-months`, `--deposit` and the rate flags). In the Projections tab it is the "focal grant" kind of the Add form (`cmd/finplan/focalform.go`); its rows are read-only and can only be removed.

**Equity UI** (`cmd/finplan/equitygrants.go`, `equityvest.go`, `equityprices.go`, `equitycalendars.go`). An equity account's detail on the Accounts tab shows the equity sections instead of Record a balance (`ops.AddSnapshot` refuses the account). *Grants*: a table of the account's grants (stock, date, shares, grant price, vested and unvested shares, unvested value at `Prices.At(symbol, MaxDate)`) and a collapsible Add grant form (stock, dollar value or shares, grant price, date, calendar, first vest picked from the calendar's dates, year percents, optional cliff months, deposit account, withholding rates prefilled 22% / 5.75% / 7.65%) with a live preview of the derived shares and per-vest schedule; Add is disabled with a red reason once something has been typed (`formButton`, `grantForm.untouched`) and saves through `ops.AddGrant` by `app.addEntry`, so no undo step. Opening a grant shows its schedule from `ops.GrantSchedule` (date, percent, shares, planned or recorded, actual price and proceeds, differences); the per-vest percents are editable only while no vest of the grant is recorded (`ops.CorrectGrant`, VestPercents); Correct and Void are offered, Void after a confirmation dialog, and `ops.VoidGrant` refuses a grant with recorded vests. Record vest from a planned row prefills the date and shares, the price from the latest price and the rates from the grant (changeable) and computes V, W and N live; it records the brokerage deposit or ties to a deposit picked from the brokerage's unmatched deposits (`unmatchedDeposits`: non-void positive transactions not tied to any vest, within 14 days of the vest date, nearest first). Recorded vests can be corrected and voided; the void confirmation says the deposit and price observation stay. *Prices* (collapsible): add an observation, list newest first, correct and void. *Vest calendars* (collapsible): pick or create a calendar, name, one rule per vest month, the dates it generates for the next three years with a per-date Move to override, Save and Delete; these go through `app.edit` and are undoable (`app.edit` takes a documents step when `Calendars` change). `ops.EditCalendar` refuses a rule change that moves a grant's first vest off the calendar, and a draft override of a date the rules no longer generate is dropped on save.

**Undo of a vest.** Recording a vest (`app.recordVest`) is one undo step, an exception to "entries push no undo step": undo voids the vest and the deposit and price observation that recording created (a fact already void stays the user's); redo restores only what undo voided, vest first, stopping at the first refusal so a deposit is never restored without its vest (`restoreFacts`).

**Rules `ops` enforces.** Voiding a grant is refused while it has non-void vests. Correcting a grant that has recorded vests is refused (`in_use`) if it would change the plan's dates, percents or length, or move the grant date after a vest. Deleting a calendar is refused while a non-void grant uses it, and editing one is refused if that would break a grant's plan. An account with grants, or the brokerage account of a grant, cannot change type and cannot be deleted.

## Analysis tools

In build order:

1. **Single projection:** an asset's curve plus the breakdown for any interval.
2. **Compare:** several projections and reality on one graph, and the difference between any two.
3. **Plan versus actual:** an earlier projection against what really happened.
4. **Sensitivity:** vary one parameter across a range to get a band of outcomes.
5. **Goal solving:** for example, the earliest retirement date where money lasts to a given age.
6. **Monte Carlo:** randomized class return sequences, with realistic correlations, giving percentile bands.
7. **Spending analysis:** category trends and baselines from the record.

## UI

**Timeline strip editor (used by the Projections and Assets tabs):** a time-varying setting is shown as a timeline strip of segment blocks. Touching segments share one draggable anchor and the earlier segment's end field is disabled, since its end is implied by the next start; dragging that end back sets an end and opens a gap, and a gap gives each edge its own handle. A segment that starts at the beginning of time has no start handle. Shift-drag on an anchor moves only the earlier segment's end, opening a gap. Dragging an edge right into the next segment pushes that segment's start later; if that segment would shrink to nothing, it moves along with any later segments it meets, so nothing is deleted silently. Moving an edge left is clamped: a segment keeps at least one day, and a gapped start dragged right stops at its own last day. Drags snap to the first of a month, and Ctrl-drag moves by single days. The last segment's end handle sets the setting's end; dragging it to the strip's right edge clears it, as does a "No end" button. Clicking a segment selects it; the selected segment has typed From and To date fields (YYYY-MM-DD) beside its value field: From reads "beginning" and is not editable for a segment that starts at the beginning of time, To shows the segment's last day and is empty ("no end") for an open last segment, and clearing it on the last segment clears the end. A typed date lands exactly, with no month snap and no clamp to the strip's range, and the strip's span (`timeline.Span`, unchanged) grows to show it. It pushes later segments along as a drag does, and a From past the segment's own last day moves the segment keeping its length. A date that cannot be applied (an end before the segment's From, a From on a beginning-of-time segment, a From that would empty or overlap the segment before, or text that is no date) is refused with a reason and changes nothing. The selected segment also has Split (at the midpoint, snapped to a month, both halves keep the value) and Delete, and the Delete key removes it too; deleting the only segment is refused. "Add after last" appends a segment with the last one's value. **Budget tab:** shows the base budget (`Record.Budget`), which every projection builds on. **Editing and undo:** every edit on the Projections, Assets, Accounts and Budget tabs goes through `internal/ops` (see "Shared edit operations" below) by way of one GUI path, `app.edit`. `ops` validates the edit, applies it to a copy of the record's editable documents and saves the copy; only if that succeeds does `app.edit` make the new record the live one, rebuild the Graph's data and push one undo step; the Graph keeps its lines, preset and range. A change that changes nothing (`ops.ErrNoChange`) makes no step, and a failure shows a notification and leaves everything as it was. Edit > Undo and Edit > Redo (labelled with the step, for example "Undo rename projection") and Ctrl+Z, Ctrl+Shift+Z and Ctrl+Y save through `ops.RestoreProjections`, or, for a step that changed accounts, assets or the base budget, through `ops.RestoreDocuments` (`Record.WithDocuments`), which restores the accounts, assets, base budget and projections and keeps the record entries added since, move the history only after the save succeeds, and restore the Graph's projection switcher as it was in the step; the shortcuts are ignored while a text field has focus or any popup, modal dialogs included, is open (`shortcutsBlocked`). A delete of an asset or account is one undo step: the step keeps the records before and after it, and undo and redo restore accounts, assets, base budget and projections (asset settings, modifications and added items) through `ops.RestoreDocuments` and `Record.WithDocuments`. Undo history is cleared by any reload of the record, including one caused by another program changing the database. The GUI's edit path keeps only window concerns: the undo history, rebuilding the Graph's data, the switcher memory, and renaming the in-memory Graph lines and loaded presets. Renaming a projection also updates its children's parent (in `ops`), the Graph's lines that name it (pinned lines and the switcher) and the saved view presets; `ops` rewrites the presets after the record is saved, and a failed write shows a notification. A delete that removed lines from saved view presets also keeps those presets as stored before and after (`ops.Result.Pruned`); undo and redo put them back through `ops.PutPresets`, and a preset changed or deleted since the step is left as it is, with a notification naming it (`app.restore`). Deleting a projection leaves the Graph lines pinned to it in place; they draw nothing until the delete is undone. Adding, correcting, voiding or restoring an entry (`app.addEntry`) pushes no undo step, because entries are append-only; one is corrected or voided instead. The exception is recording a vest (see "Equity: RSU grants"). `ops.RestoreDocuments` also refuses (`ErrInUse`, naming the grant) an undo or redo that would leave a live grant with a missing calendar, an unplannable schedule, a non-equity account or a deposit account that is missing or not a brokerage. An undo or redo that would remove an account that has record entries, or that another account's entry names as counter, is refused with a notification. Not built yet: shocks and rebalances, the Markets tab, and on the Budget tab the comparison of actual spending with the budget and transaction matching (both wait for SimpleFIN transactions).

The smoke test runs every case with it. A form's Add button (`formButton`) is disabled while the input is invalid but shows its red reason only after the user has typed in the form: the four Projections forms (modification, new budget item, projection account, start setting) and the Budget tab's Add form, as the Assets and Accounts forms already did.

**Shared edit operations:** `internal/ops` is the single way editable data changes: projections, accounts, assets and the base budget, and record entries by way of corrections. The GUI calls it, and the CLI's write commands call it too; it does not depend on the GUI, so an edit is validated, applied and saved the same way whoever makes it. Every operation takes the loaded record and the store, validates its input, applies the change to a copy, saves the copy in one transaction and returns a `Result` with the new record and the changed object: the projection, account, asset or budget item (and, for a rename, the rename, the presets rewritten and any preset warnings). The record passed in is never changed. On any failure nothing is saved and the error says why; a failed save is an `ops.SaveError`. Every operation takes `Options`; with `DryRun` it validates and applies to a copy and returns the same result without saving the record or writing presets. An edit that changes nothing returns `ErrNoChange` and saves nothing.

The operations: new, clone, rename and delete projection; set parent, start, override_history and inflation (nil removes it); add a modification; check a modification or a budget item without saving (`CheckMod`, `CheckItem`, the validation the Add form shows); list the budget items available at a position of a projection's modifications (`ItemsBefore`); replace a modification, including its object and property (`SetMod`); set a modification's values (its value and start); set a modification's mode (`SetModMode`, with optional replacement values); move and remove a modification; and restore a projection list (used by undo and redo). The rules `ops` enforces: names are trimmed and must be non-empty and unused; an unknown projection or parent is refused; delete is refused while another projection builds on it; a parent change that makes a cycle is refused; a modification on anything but a global needs an object; values must be finite and at most 1e15 in magnitude; a mode must be set or scale (scale is refused on `add_item`, and a scale value must not be negative); a budget item raise set by a modification must be above -1; modification indexes must be in range. Rename rewrites the saved view presets that name the projection after the record is saved, each in its own write; presets that cannot be decoded are skipped, and a failed preset write is returned as a warning while the record save stands. Projection operations edit `Record.EditableCopy`; account, asset and budget operations edit a deep copy (`Record.Clone`, `editRecord`) and return `ErrNoChange` if accounts, assets and budget are unchanged. Asset, account, budget and entry operations (`internal/ops/assets.go`, `accounts.go`, `budget.go`, `entries.go`, `items.go`) add: new, rename and delete asset; add and remove member; add, edit (`EditDefault`, in place, `ErrNoChange` when equal, checked like `AddDefault` by the shared `checkInterval`), move (`MoveDefault`) and remove default interval; set or clear an asset's growth setting; new, edit, close, reopen and delete account (`accountlife.go`); add snapshot and transaction; correct and void entry (both return the reloaded record on a real run); list an account's entries newest first, with or without voided ones (`ListEntries(st, account, withVoided)`), and an entry's history (`EntryHistory(st, id)`, an unknown id is `ErrUnknownObject`); add, edit and end a base budget item; end a budget item inside a projection (`EndItem`, built on `EndMod`, the amount-of-0 modification; `EndedOn` recognises one). Rules: overlapping members are never refused (`Resolve` lists the later one as invalid); delete asset is never refused because something refers to it: `DeleteAsset` removes the asset and, in the same edit, the members naming it in other assets and the projections' asset settings and modifications for it (`unlinkAsset`), and never removes accounts; modifications of accounts under it are kept; delete account of an account without record entries removes it with its default asset and unlinks it (`unlinkAccount`): members naming the account or its default asset, asset settings and modifications for either, base budget items and projection-added items whose account, from or to is the account (deleted), and the modifications, in every projection, of the items so deleted; an account with record entries (voided ones included) or that is the counter account of any stored entry is `ErrInUse` (`accountBlocked`), close it instead; `AssetDeletePlan` and `AccountDeletePlan` (`deleteplan.go`) report the same changes as a `DeletePlan` (`Affected`: kind member, asset setting, modification or budget item, the object it is `In`, a `Detail`, and the effect removed or deleted; or `Blocked`) without changing anything; close and reopen are as described under Accounts; an account's default asset (`acct:<id>`) cannot be renamed, deleted or have members changed; removing a member or asset renumbers all member seqs 1..N in order (`Record.renumber`); on a default asset the default interval operations write `Account.Default` and set-param writes the asset's params; a stated rate must be within -1..1; a transfer needs an existing counter account other than the account; a snapshot on a date that already has one is refused in favour of `CorrectEntry`; `EndBudgetItem` refuses an end before the start; item validation (`checkItemAs`) requires every amount segment above 0 and within range, every growth segment above -1, a custom count of at least 1 with a unit of days, weeks, months or years, and for semimonthly two different days from 1 to 31, and requires a start for a new item (a one-time or biweekly item's anchor serves as the start); an item that had no start keeps none unless its recurrence changes to a kind that needs a phase; an end before the start (or before the anchor when there is no start) is refused. Entries are never edited in place: correct and void call the store's `Correct` and `Void`, and their dry run uses `TryCorrect` and `TryVoid`, which run the same checks in a rolled-back transaction.

## Storage and privacy

Edits and undo or redo in the app reach the Graph without a reload: `app.install` calls `graphTab.setRecord`, which rebuilds the data cache from the new record and keeps lines, preset and range.

All app data lives in SQLite outside the repository (the app uses `$XDG_DATA_HOME/finplan/finplan.db` when `XDG_DATA_HOME` is absolute, else `~/.local/share/finplan/finplan.db`; `--demo` uses a temporary seeded database instead: a `finplan-demo-*` folder in the system temp folder with `demo.db` and an `owner.pid` file, removed on exit and on SIGINT/SIGTERM, and swept at the next demo start if its owner process is gone, `sweepDemos`). File → Backup... writes a consistent copy with `Store.Backup`. Credentials live in the OS keyring, never in files. The repository is public: real financial data never enters it, and tests and fixtures use invented numbers, such as an invented budget for a family of six.

### The storage layer

`internal/store` is a headless package, built on the pure-Go driver `modernc.org/sqlite`, that saves and loads a whole `model.Record`. `store.Open(path)` takes a path, creates or migrates the database, sets WAL mode, foreign keys and a busy timeout, and fails if WAL did not take. The store has one connection and is safe for concurrent use. `Save(record)` and `Load()` are the main calls; each runs in one transaction.

**Record versus documents.** The record proper, balance snapshots and transactions (with their kind, counter and memo), is append-only. Everything else is a freely editable document: account attributes, assets, the budget, projections, market classes, globals. Real tables hold the record so that it can be queried by account and date and so that the database itself enforces append-only. Versioned JSON holds the documents because they are nested, freely edited and versioned per document. An account document has no owner; a stored database that still has one opens, and the value is dropped (unknown fields are ignored, with no format change). A record whose stored `Today` is unset (0, or no record document) loads with `Today` set to the current date, each time, and a save of a record still holding that date stores it unset again (`Store.Load`, `saveRecord`); a stored nonzero date, like the demo's fixed one, loads unchanged.

**Schema.** The schema version is `PRAGMA user_version`. Migrations are a numbered, forward-only list applied in one transaction on `Open`; a released migration is never edited. A database newer than the code fails with `ErrFutureSchema` and is left untouched. Migration 1 creates:

- `entries`: one row per snapshot or transaction, indexed by (account, date).
- `corrections`: the full replacement values, a note and the time made, referencing an entry.
- triggers that reject UPDATE and DELETE on both tables.
- `documents`: kind, key, ordinal, format version and JSON body.

Migration 2 adds `presets`, kept apart because `Save` replaces the documents wholesale. Migration 3 adds `corrections.void`. Migration 4 (schema version 4) adds `facts` and `fact_corrections` for the equity facts: grants, recorded vests and price observations. They are append-only like entries (triggers reject UPDATE and DELETE). A fact's body is JSON; a correction carries the whole new body, a note and a void flag, the latest correction wins and the history stays (`Store.CorrectFact`, `VoidFact`, `FactHistory`). Vest calendars are not facts but documents.

**Saving the record.** `Save` replaces every document and appends the model's entries that are not yet stored. It matches the stored entries of each account (with corrections applied) against the model's as a multiset of values. If a stored entry was changed or removed in the model, or an account that has stored entries is gone, `Save` fails with `ErrRecordChanged` and writes nothing. Changes to stored entries go through corrections.

**Corrections.** `Entries(account)` lists an account's entries with their ids and current values. `Correct(id, values, note)` appends a correction, stamped with the time made, that holds the full replacement values; the original and earlier corrections stay. `Correct` rejects an unknown id (`ErrNotFound`), a snapshot correction that carries a transaction kind, counter or memo or would give the account two snapshots on one date, and a transfer with no counter account. `History(id)` returns the original and then each correction in order. `Load` applies the latest correction to each entry. `Void(id, note)` records a void correction: voided entries are left out of `Entries` and `Load` but stay in `History`, and a later correction restores the entry.

**Stale records.** `Load` records a marker, the highest `corrections.id`. `Save` returns `ErrRecordChanged` if the model still holds a value of an entry voided or corrected (any correction with an id above the marker) since that `Load`. A genuinely new entry equal to an entry voided before the last `Load` saves normally.

**Change polling and backup.** `DataVersion()` returns SQLite's `data_version`, which changes when another connection commits, for polling. `Backup(path)` runs `VACUUM INTO` a temporary file in the target folder and renames it into place, so a failure leaves an existing file untouched; it refuses the store's own database file.

**Versioning and loading.** Each document row carries its own format version, and decoding dispatches on it. The current format is 5, which stores a budget item's amount and growth as segment arrays and adds a custom recurrence's count and unit (older documents have numbers there, which load as a one-segment schedule, a growth of 0 as none; an older build refuses format 5); format 4 added an account's close date (older documents have none and load as open accounts); format 3 added the accounts a projection defines to its document (formats 1 and 2 have none and load as an empty list); format 2 added a modification's `mode` and a budget item's `growth`. Formats 1 to 5 all load (base budget items and the items a projection adds are migrated alike), a missing mode loads as `set` and a missing growth as none, and an unknown mode is an error. A later format adds a case that reads the old shape and converts it. A row with an unknown format fails with `ErrUnknownFormat` rather than being dropped. The stored shape is a set of DTOs separate from the model types, so renaming a model field does not change what is on disk. `Load` rebuilds the record through the model constructors, replaying members in their original `Seq` order, so the loaded record equals the saved one; an empty database loads as an empty record.

**View presets.** `PutPreset`, `Preset`, `Presets` and `DeletePreset` store opaque bytes under a name with a format version owned by the writer. The store does not interpret them and does not import `internal/graph`. The app stores them as JSON in `PresetFormat` 1 (`graph.EncodePreset`, `graph.DecodePreset`; an unknown format is an error). `Restore` skips lines the record no longer has and the bands that use them, and falls back to another switcher if the saved projection is gone.

**Not done yet.** There is no delete correction (entries can be voided); and holdings (other than the equity facts above), life events and a manual-versus-synced distinction have no storage because the model has no types for them yet.

## CLI and agent access

The `finplan` binary doubles as a CLI: with no subcommand (`finplan`, `finplan --demo`) it opens the GUI, and a non-flag argument routes to the CLI (`main`, `isCLI`; the values of `--db` and of the GUI's screenshot flags such as `--screenshot x.png` are not commands, so `finplan --demo --screenshot x.png` is the GUI in screenshot mode, see the README), which does one job through the shared library and exits. Every command prints one JSON document on stdout; errors are `{"error":{"code","message"}}` on stdout, with exit 2 for usage errors and 1 for all others. The codes are `usage`, `not_found`, `ambiguous`, `no_database`, `old_schema`, `future_schema`, `database` and `engine`; the write commands add `unknown_target`, `name_taken`, `has_children`, `cycle`, `invalid`, `in_use` and `record_changed`.

Commands are data: `cmd/finplan/cliread.go` holds the read command table and `cmd/finplan/cliwrite.go` the projection write commands and `cmd/finplan/cliwritedata.go` (`dataCommands`) those for assets, accounts, entries and the base budget (name, summary, arguments, flags, output shape, whether it writes, its JSON input), and both the parser and `finplan help` / `finplan help --json` are generated from it, so the reference cannot drift from the code.

**Global flags.** `--demo` (a throwaway seeded database, removed on exit) and `--db <path>` work on every command, before or after it; using both is a usage error. With neither, the real database is used (`$XDG_DATA_HOME/finplan/finplan.db`, else `~/.local/share/finplan/finplan.db`).

**Read commands never write.** They open the database with `store.OpenReadOnly`, which never creates, migrates or writes it. A missing file is `no_database` and is not created; a schema older than the code is `old_schema` (the message asks you to open the database with the app first, which migrates it); a newer schema is `future_schema` (`store.ErrOldSchema`, `store.ErrFutureSchema`).

**Output conventions.** Dates are `YYYY-MM-DD`, `null` when absent or unbounded. Statuses are lowercase: `default`, `actual`, `projected`, `partly_projected`. Reality appears as `"projection": null`.

**Commands.** Commands about data that belongs to one kind of object are noun-verb; the engine queries are top-level verbs because they accept either an asset or an account.

    finplan account list                  # [{id, name, type, tax, stated_rate, default}]
    finplan account entries <account> [--voided]  # [{id, kind, date, amount, tx_kind, counter, memo}], voided entries left out; --voided includes them with a void field
    finplan entry history <entry-id>      # {id, revisions: [{date, amount, tx_kind, counter, memo, made_at, note, void}]}
    finplan asset list                    # [{id, name, kind, members, invalid, error, default, params}]
    finplan asset params <asset>          # {asset, default, growth, today, accounts: [{account, name, layers, effective, today}]}
    finplan budget list                   # [{id, name, kind, amount, amount_schedule, recurrence, start, end, indexed, growth, growth_schedule, account, from, to}]
    finplan budget totals                 # {as_of, monthly_income, monthly_expenses, monthly_net}
    finplan projection list               # [{name, parent, start, override_history, modification_count}]
    finplan projection show <name>        # settings, asset_settings and modifications in the order they apply
    finplan balance <target> --from 2026-01 --to 2060-12 [--step day|week|month|year] [--projection P]
                                          # {target, projection, from, to, step, samples: [{date, value, status}], diagnostics}
    finplan breakdown <target> --from 2026-01 --to 2026-12 [--projection P]   # causes: income, expense, transfer, contribution, withdrawal, grant, vest, tax, growth, opening, unexplained, default
                                          # {target, projection, from, to, start, end, total, lines: [{cause, actual, projected}], diagnostics}
    finplan starts [--projection P] [<target>]
                                          # [{account, start, last_actual, has_actual, override_history, projection_start}]
    finplan help [--json]

`--step` defaults to `month`. `diagnostics` is `{skipped: [...], overlaps: [...]}`: modifications the engine skipped and invalid asset members.

**Targets.** A `<target>` is accepted by id or display name; ids win over names. An account and its default asset count as one object. A name that matches several objects is an `ambiguous` error (`findCandidates`, `resolveTarget`). `account entries` takes an account only.

**Dates.** Dates are `YYYY-MM-DD` or `YYYY-MM`. For `--from`, `YYYY-MM` is the first of the month; for `--to`, the last day. Month and year steps keep the start's day of month, clamped to the month's end, and are computed from `--from` each time so a clamped day does not carry forward (`parseCLIDate`, `sampleDates`).

**Database.** A write command opens the database with `store.Open` (`openWrite`): it migrates an older database but never creates a missing one (`no_database`); `--demo` and `--db` work as for reads. Read commands still never write.

**Dry run and output.** Every write command takes `--dry-run`: the edit is validated and applied to a copy, and nothing is saved (`ops.Options`, `commit`). A dry run runs the same checks as a real write, including `store.CheckSave`, which checks that the record could be saved and restored without writing it. It never migrates: `openWrite` checks the schema read-only first and refuses a database that needs migrating with `old_schema`. The output of the projection commands is `{dry_run, changed, projection}`, the projection in the shape of `projection show` after the edit; the other write commands print `{dry_run, changed, <object>}` with `asset`, `account`, `entry` or `item` built by the same functions as the read commands (`assetJSON`, `accountJSON`, `entryJSON`, `budgetItemJSON`); `asset delete` and `account delete` add `removed` and `affected`, `entry void` adds `voided`, and an entry added in a dry run has id null. An edit that changes nothing (`ops.ErrNoChange`) prints `changed: false` and exits 0. `projection rename` adds `renamed {from, to}`, `rewritten_presets` and `warnings` (presets that could not be rewritten; the rename is saved regardless); `projection delete` prints `removed` and the projection as it was.

**Deleting assets and accounts.** `asset delete` and `account delete` first compute the plan (`ops.AssetDeletePlan`, `AccountDeletePlan`; `confirmDelete`). A plan that is `Blocked` (an account with record entries or named as counter account) is `in_use` whatever the flags. Without `--force`, a plan with affected objects fails with exit 1, code `confirm_required` and the list as `error.affected` (`cliError.Affected`); a delete with nothing affected runs. `--dry-run` prints the plan without saving, and `--force` performs the cascade. The plan also lists the saved view presets that lose lines (kind "view preset"; see View presets), and the delete removes those lines from them. The success output includes `affected`, a list of `{kind, in, detail, effect}`.

**Errors.** `opsError` maps the operations' errors to codes: `not_found` (unknown projection, asset, account or entry), `in_use` (deleting an account with record entries or that is the counter account of an entry; removing an account from a projection while a modification, item or asset setting of it or of a projection building on it uses it), `failed` (the generic code `runCLI` gives any error that is not a coded CLI error; exit 1), `confirm_required` (a delete that changes other objects, without `--force`; see "Deleting assets and accounts"), `record_changed` (the stored record changed since it was loaded), `unknown_target`, `name_taken`, `has_children`, `cycle`, `invalid` (out-of-range values, a missing object, an empty name) and `database` (the save failed). Usage errors exit 2, all others 1.

**Input.** Rates are fractions (`0.03` for 3%); a negative rate argument needs `--` before it. A modification's values are a constant (`--value`, optionally `--from` and an inclusive `--end`; `--end` needs `--value` and `--from`) or a schedule as JSON on stdin or `--json-file`, `[{"from","end","value"}]`; a budget item is given by flags or as JSON in the shape `budget list` prints. JSON is decoded strictly (unknown fields and trailing data are usage errors).

**Modes and growth.** `mod add --mode set|scale` (default `set`); `growth` is accepted for item targets (a raise). `mod edit --mode` alone keeps the values; with `--value` or `--json-file` it replaces them too (`ops.SetModMode`). Growth values are annual fractions (0.03 is 3%) and scale values are multipliers (0.7 cuts by 30%). `--growth` is an item flag on `item add`/`item edit` and `budget add`/`budget edit`, and `growth` is a field of item JSON. Output carries `mode` on modifications and `growth` on items. `projection set-inflation` acts only on the set-mode inflation modification, inserting a new one before the first scale inflation modification; scale ones are kept and still apply.

**Item flags and JSON.** `--every` is one-time, weekly, biweekly, semimonthly, monthly, quarterly, annually (`annual` is the same) or custom; `--start` is the first date (`--on` is the same flag, giving both is an error), and `--day`, `--day2` (semimonthly), `--count` and `--unit` (custom) complete the recurrence (`itemFlags`, `recurrenceFor`). An add needs a start; an edit without a date flag keeps the item's start, anchor and annual month and day. `--amount` and `--growth` are single numbers; schedules come as JSON. In item JSON `amount` and `growth` are a number or `[{from, end, value}]` (a null or absent `from` means from the beginning, and an empty list is the empty schedule; `projection show` and `budget list` print such a schedule with a null `from`, so it round-trips), and `recurrence` gains `count` and `unit`. Output adds `amount_schedule` and `growth_schedule` and prints `amount` and `growth` as the value in effect on the record's today (0 if none), so `budget list` output round-trips into `budget edit`; when input gives both a number and a schedule they must agree on that value or it is refused (`itemFromFlags`, `itemInput`, `scheduleOf`, `valueListed`).

**Budget items.** `item add` stores a new item as an `add_item` modification (`ops.AddItem`, `checkItem`). Kinds are income and expense (which need an account) and transfer (from and to; at least one an account of the record). Recurrence is one-time, weekly, biweekly, semimonthly (day and day2), monthly (day), quarterly, annual (month and day, checked against the month) or custom (count and unit), with a required start and an optional end; amount and growth may be schedules. A one-time item happens on its date (the recurrence anchor); a start, if given, must equal it, otherwise it is `invalid`. An id not given is a unique slug of the name. `item edit` (`ops.EditItem`) replaces an item the projection itself adds and keeps its id. `item end` (`ops.EndItem`) appends an amount modification of 0 from the date, for a record item or one added in the chain.

**Asset settings and missing targets.** The `asset-setting` commands call `ops.AddAssetSetting`, `InsertAssetSetting` (with `--at`), `SetAssetSetting`, `MoveAssetSetting` and `RemoveAssetSetting`. Indexes count from 0, as `projection show` numbers `asset_settings`; a bad index is `invalid`. `--asset` takes an id or name (an account names its default asset) resolved in the projection's view, hypothetical accounts included. Settings apply in list order and the last applied wins. A setting with neither a start nor an override_history is refused (`invalid`), as is an asset the projection's view does not have (`unknown_target`). `budget delete <item>` (`ops.DeleteBudgetItem`) deletes a base budget item and prints `{dry_run, changed, removed, item}`, the item as it was; it is not refused when a projection modifies the item, and that modification is left dangling. `projection show` (and the projection in a write's output) gives each modification `missing` and, when true, `missing_target` naming it, such as "budget item salary-a". A budget-item amount or growth modification is missing when the item is neither in the base budget nor added by an `add_item` earlier in the chain; an account or asset modification when the target is not in the projection's view; a global one never (`Record.MissingTargets`). The engine skips the same modifications and lists them in `diagnostics.skipped` with a reason.

**Modification targets.** The operations check that the property suits the target (amount or growth for a budget item, growth or default for an account or asset, growth for a stock, inflation for global, add_grant for an equity account) and that the target resolves at the modification's position (`checkTarget`): a record budget item, an item added by an ancestor's `add_item` modification, or one added by an earlier row of the same projection; otherwise `unknown_target`. `mod add` cannot add an item. Every edit then checks (`checkNoNewDangling`) that no modification which resolved before stops resolving, which refuses moves, removals, parent changes and removals of added items that would orphan a modification; modifications already dangling do not block an edit, including rename and clone.

Record writes are the `entry` commands: snapshots and transactions are appended, and changes to them go through corrections (`entry correct`, `entry void`).

Equity writes (`cmd/finplan/cliequity.go`) go through `ops` as well: `calendar new|edit|delete`, `grant add|correct|void`, `vest record|correct|void` and `price add|correct|void`, each with `--dry-run`. Calendar rules are written like `mar=3mon`, `jun=lastfri`, `feb=15` and overrides as `2027-03-15=2027-03-16`. Rates are fractions (`0.22`); year and vest percents are percent units (`25,25,25,25`). The reads are `calendar list`, `calendar dates`, `account grants`, `grant schedule`, `grant history`, `vest history`, `price history` (`--voided`) and `price revisions`. Grants, vests and prices share one id numbering.

The agent (Claude) has full access: it reads the record, assets, budgets, projections and engine output, and writes through the write commands: projections (settings, modifications and added budget items), assets, accounts, the base budget and record entries. Changes to recorded entries go through corrections, like the GUI's. Whatever the agent reads is sent to its model provider.

A thin agent skill lives in this repository at `.claude/skills/finplan/SKILL.md`: what finplan is, the rules (use the CLI, never touch the database; record changes are corrections), and an instruction to run `finplan help --json`, which the binary generates so the command reference cannot drift from the code. Symlinking the skill into `~/.claude/skills/finplan` makes it available in any terminal.
